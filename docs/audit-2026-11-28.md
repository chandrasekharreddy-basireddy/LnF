# The external hardening patch (28/11, later)

`lnf-full-hardening.patch` (116 KB) was written against an older commit and creates
`supabase/migrations/0020_audit_remediation.sql` and `0021_deep_hardening.sql`. Both numbers are
already taken here (chat, bulk import), and 20 of its 38 files have moved since. `git apply`
fails on 11 files, so applying it would have regressed the chat, the importer and the previous
remediation.

What I did instead: read every hunk, keep what is genuinely better, port it as `0023`, verify each
piece against the live database.

## Ported

| Change | Why it is better |
| --- | --- |
| `scan_message` phone pattern | it missed `+91 98765 43210` and `98765-43210` — a split number is exactly how a scammer writes it |
| `scan_message` PAN pattern | case-insensitive and boundary-anchored; `pan abcde1234f` slipped through before |
| `create_found_item_anonymous` | default date in IST, and an empty IP now falls back to `anon-global` instead of skipping the throttle |
| `queue_email_retry` | event-type allowlist plus 10/hour; it accepted any event name and had no limit |
| `request_account_deletion()` | erasure goes through an RPC with a rate limit and duplicate check, instead of a raw table insert from the browser |
| `notifications` UPDATE | column-scoped to `read_at`; the owner could rewrite the body |
| `saved_searches` / `abuse_reports` writes | revoked; the RPCs are the only writers |
| `has_role()` | internal predicate, no longer executable by clients |
| `src/lib/client-photo.ts` | compresses photos on the phone before upload |

That last one is the most useful thing in the patch, and it corrects a mistake of mine: I raised
`serverActions.bodySizeLimit` to 16 MB, but **Vercel rejects request bodies over ~4.5 MB before
the action runs**, so the setting could never help. Compression on the client is the fix that
actually works, and it also cuts Supabase Storage use.

Verified after porting: `98765 43210`, `+91-98765-43210` and `abcde1234f` are all caught;
`found near the library gate` is not; `notifications.read_at` is updatable and nothing else is;
`saved_searches` insert is refused.

## Deliberately not ported

**Revoking execute on `check_signin_allowed()` and `log_auth_event()` from `anon`.** Our sign-in
path calls both with the visitor's session *before* an account exists. Revoking them breaks
sign-in entirely — and those two functions are the throttle protecting the form. The patch may
have moved those calls to a service-role client; we did not, and the anon grant is what makes the
flow work.

## Still open from that patch

`admin_erase_user_data()` (the patch does not implement it either — it only adds the request RPC),
the storage-queue cron drain, the dark-mode `@media` mirror, `React.cache`, and age-encrypted
backups. Same reasons as above.

**applies cleanly**. 21 files, one new migration (`0035`), plus the push/PWA pieces

## What it fixed, all real

| --- | --- |

It called `public.phash_distance(...)`, which does not exist — the distance function is
`photo_distance(bigint, bigint)`, and `item_photo_distance(uuid, uuid)` already existed from 0029.
Corrected before applying; the migration would otherwise have failed atomically, which is how it
announced itself.

## Verified on the live database

`push_subscriptions` and `disputes` are no longer selectable by `authenticated`; the endpoint CHECK
exists; `refresh_matches` carries `public, extensions`; and a hostile endpoint
(`https://evil.example.com/collect`) is **rejected by `push_endpoint_allowed_host`** with keys long
enough to pass the shape checks — so it is the allowlist doing the work, not a side effect.

## Two bugs the patch brought with it

Both were caught, and both are worth recording because they show what each gate is for.

| Bug | How it surfaced | Fix |
| --- | --- | --- |
| `isAllowedPushEndpoint()` **called itself** as its first check — a stack overflow, not a guard. Every push subscription test failed with `Maximum call stack size exceeded` | CI. The local vitest cannot start in this pod, so CI was the only thing that ran them | shape checks first (https, no whitespace, bounded length), then the URL parse and host allowlist |

# Gemini audit #2 (28/11, 11:28 IST) — commit 627d3a6, 84/100, 1 Critical

The Critical was mine, and it was the third time for the same bug.

## CRIT-01: `create_item` could not hash

`0038` re-created `create_item` from its `0022` body, which carries
`set search_path = public`. pgcrypto lives in `extensions`, so `digest()` was unreachable and
**every report failed with 42883**. Not a corner case — the main write path of the product.

History of this exact bug: `0017` fixed it → `0022` reintroduced it → `0025` fixed it → `0038`
reintroduced it. A patch each time was never going to hold, so `0039` adds two things beyond the
repair:

1. `scripts/check-search-path.mjs` — reads the migrations in order, tracks the **last** definition
   of each `SECURITY DEFINER` function that calls `digest()`, honours later `ALTER … SET
   search_path` statements and the sweep, and **fails the build** if any of them cannot reach
   pgcrypto. Wired into CI.
2. The same sweep, run again, with `assert_write_paths_hashable()` as the database-side probe.

Verified: `create_item` created `LF-2026-0025` on the live project, then the probe row was deleted.

## HIGH-01: the offline sheet's dark theme was declared above the light rules

My own fix from the previous pass put `@media (prefers-color-scheme: dark)` at the *top* of the
stylesheet, so the base light rules that followed it won. Moved to the end.

## MED-01: the throttle key, again

`0038` said "last hop" in a comment and hashed the whole `x-forwarded-for` chain — the comment and

# Closing the residue (28/11, afternoon)

## The gate that was missing

Every finding this session has had the same shape: **SQL that nobody ran**. The `search_path` bug
survived four passes; the erasure regressed twice; the import lost its guards twice. Reading the
code caught some of it, an external audit caught the rest, two hours later.

CI now runs the migrations against a real Postgres:

- `supabase/tests/00_bootstrap.sql` builds the Supabase shape — `auth`, `storage`, `cron`, the three
  roles, pgcrypto in `extensions`, `auth.uid()` reading the JWT claim — on `postgres:16`
- `scripts/sql-check.sh` applies all 42 migrations in order, then asserts
- `supabase/tests/99_assert.sql` checks RLS on every personal table, that
  `push_subscriptions` and `disputes` are unreadable by a member, that
  `admin_erase_user_data` and `bulk_import_items` are uncallable by anon, that `has_role()` is not
  client-callable, the one-approved-claim index, the push endpoint allowlist, `code_plain`
  nullability — **and then calls `create_item` and asserts the answer was hashed.**

That last line is the whole point: it is the exact call that failed in production.

It paid for itself on its first three runs, by finding two genuine portability bugs in `0004`:

1. a `VALUES` list yields `text` for string columns, so inserting into `item_type` needs a cast
2. a column that is `NULL` in every row is typed `text`, so `reporter_id` could not go into a `uuid`

Neither could have been caught by reading, and both would have failed a fresh environment.

## Also closed

- `templates.matchAlert` was never queued by anything: a finder logging the right item produced an
  in-app notification and silence everywhere else. `0042` adds `queue_match_alerts()`, an idempotent
  bounded sweep keyed on `match_alerts.notified_at`, called from the housekeeping cron.
- the command palette let Tab walk out into the page behind it, so a "modal" was not one. Focus is
  trapped now.

## Not done, and why

- **React 19 form resets after a submit** — I added a ref to fix it, then removed it: the behaviour
  needs a browser to confirm, and chromium cannot load an http URL here. A guess that looks like a
  fix is worse than a recorded gap.
- **Mobile 360px polish and dark-mode pixels** — same reason.
- **`claim_messages_read` RLS for non-staff** — needs a session to test, and the chat already
  degrades to polling.
